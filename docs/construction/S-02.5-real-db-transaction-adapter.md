### EXTERNAL-RESEARCH
PostgreSQL 17 documentation (2026):
- transaction blocks keep related statements atomic;
- SERIALIZABLE is supported and serialization failures require complete transaction retry;
- SELECT FOR UPDATE provides row-level write/lock protection;
- UNIQUE, FOREIGN KEY and CHECK constraints are database-enforced.
Design consequence: DB constraints and transaction lifecycle are authoritative; retries happen at the transaction boundary, not around individual statements. citeturn0search0turn0search4turn0search24

### THREAT-GATE
- Asset: posted money, contribution state, provider-event identity, receipt evidence, outbox event.
- Trust boundary: application process → PostgreSQL.
- Replay/double execution: organization/idempotency and provider/event constraints.
- Cross-org access: every settlement lookup/update includes organization scope.
- Concurrency: SERIALIZABLE + row locks + DB unique constraints.
- Provider lies/repeats: provider event is accepted only after upstream signature/status/amount/currency checks; duplicate events are transactionally claimed.
- Failure: rollback leaves no partial financial state.
- Evidence: ledger transaction, fee snapshot, receipt, provider event and outbox survive only together after commit.
- Safe failure: pending/quarantined provider state, never a speculative ledger post.

### DESIGN
Transaction lifecycle:
BEGIN → lock → idempotency → claim provider event → ledger → fees → state → receipt → outbox → COMMIT.
External provider calls remain outside the transaction.

### TEST / SECURITY
Added deterministic tests for:
- serializable BEGIN/COMMIT;
- rollback on mid-transaction failure;
- transaction identifier capture;
- complete transaction retry on SQLSTATE 40001;
- no retry of persistent validation errors.

The migration encodes uniqueness, foreign keys, exact monetary storage and status checks.

### OBSERVE / COST
The transaction context exposes PostgreSQL txid_current() for correlation. The adapter performs no provider calls and uses bounded retry (default 3 attempts), avoiding uncontrolled retry storms.

### Remaining risk
This brick does not yet prove behavior against a live PostgreSQL server. A real PostgreSQL CI integration test is the next persistence hardening step before provider adapters are treated as production-ready.
