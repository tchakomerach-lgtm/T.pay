# P057.2 — Runtime RLS for device/session authentication

## Purpose
Move the production session-validation read path from the database owner context to the existing least-privilege `tpay_school_runtime` role. This is a continuation of L13.1 and P057.1, not a second identity implementation.

## Runtime contract
1. Parse the tenant routing segment from the versioned bearer. It is untrusted.
2. Open one PostgreSQL connection and begin a transaction.
3. `SET LOCAL ROLE tpay_school_runtime`.
4. Set transaction-local `tpay.tenant_id` from the untrusted routing segment.
5. Query the complete bearer hash and require exact tenant match; lock the matched session/device rows for the duration of validation.
6. Update only `api_sessions.last_seen_at` under the same tenant RLS policy.
7. Commit; on any failure rollback and reject authentication.

The production repository adapter has no unscoped query fallback. If tenant transaction support is absent, validation throws `AUTH_TENANT_TRANSACTION_REQUIRED`; direct repository queries in the production adapter are disabled.

The session hash is the authentication proof. The tenant segment alone grants no access.

## Database controls
Migration 125 enables and forces RLS on `api_devices` and `api_sessions`. Runtime can SELECT devices and sessions and UPDATE only the session last_seen_at column. There is no runtime INSERT, DELETE, credential mutation or device revocation grant in this migration.

## Legacy migration compatibility finding
The existing files 054–056 reference a legacy `fortress_vaults` table, while migration 047 defines the active `tpay_vaults` model and the repository contains no migration creating `fortress_vaults`. The implementation does not invent a second vault schema. The migration runner now records an explicit `conditional-skip:legacy-schema-absent:fortress_vaults` marker for 054–056 only when that legacy table is absent. If the table exists, those migrations still execute unchanged. This unresolved legacy-vault path must be reconciled with the Security Bible before any legacy user-data vault functionality is claimed.

## Deployment prerequisite
- `TPAY_DATABASE_URL` is the API runtime pool and must use a non-owner, non-superuser, NOBYPASSRLS login.
- `TPAY_MIGRATION_DATABASE_URL` is a separate migration-only connection. Production startup requires it and applies migrations through a short-lived client; the API request pool never runs migrations with its runtime credentials.
- The API login must be explicitly granted membership in `tpay_school_runtime`. Do not grant that membership to a broad administrative login. If role switching or tenant GUC setup fails, authentication fails closed.
- Local-only insecure bootstrap remains gated by the existing explicit local-test flags.

## Scope limits
This brick does not yet force RLS on `education_actors`, because repository workers and existing actor lookup paths must first be migrated to transaction-scoped tenant context. The API actor lookup now runs under `tpay_school_runtime` with explicit tenant and organization predicates. Full actor-table RLS is a separate P057 gate after a complete caller inventory.
WebAuthn challenge persistence, passkey counter/replay protection, refresh rotation, HTTP session revocation, recovery and terrain evidence remain outstanding.
