# S-03.3 — Provider Event Validation + Durable Replay Claim

## Goal

Harden the boundary between an authenticated provider callback and financial settlement so provider evidence cannot settle a different organization, payment, reference, amount, currency or workflow state.

## Construction gate

`verified callback → server-side payment lookup/lock → provider-event identity validation → durable unique(provider,event_id) claim → atomic financial settlement`

The durable replay claim remains inside the same PostgreSQL transaction as ledger settlement. A validation mismatch occurs before the claim, so an invalid event is not consumed as if it were a legitimate processed event.

## Implemented

- explicit provider identity validation against the payment intent;
- payment ID and provider reference matching;
- exact amount/currency matching;
- organization binding;
- accepted-state gate;
- persisted payment/contribution organization checks after row locks;
- persisted idempotency-key consistency checks;
- existing PostgreSQL unique `(provider,event_id)` replay barrier retained;
- duplicate/replay path returns the settled result only when the organization-scoped ledger idempotency record exists;
- mismatch negative tests.

## Threat gate

| Threat | Control |
|---|---|
| cross-provider event | provider must equal the server-side payment provider |
| cross-organization event | request organization and locked persisted payment/contribution organization must match |
| wrong payment | event payment ID must equal locked payment intent |
| reference substitution | provider reference must equal server-side provider reference |
| amount/currency tampering | exact bigint amount and currency comparison |
| pending event treated as payment | only `accepted` reaches settlement |
| replay | unique PostgreSQL `(provider,event_id)` claim inside atomic transaction |
| concurrent duplicate | database uniqueness is authoritative; application memory is not |
| invalid event consumed | validation happens before the durable replay claim |
| duplicate after settlement | ledger idempotency is checked before financial side effects |
