## Décision
Créer un instantané métier déterministe et autonome à partir d'un résultat de période P056.7 COMPLETE. L'instantané fige l'identité académique minimale, la marque de l'établissement, la version du modèle, le contexte de classe/période et les résultats calculés. Le SHA-256 est calculé sur une représentation canonique à clés triées. L'ordre des matières ne modifie donc pas l'empreinte.

## Invariants
1. Un bulletin ne peut pas être préparé si le résultat de période ou une matière requise est incomplet.
2. Le module ne recalcule pas les notes : il consomme le contrat P056.7.
3. Les matières sont ordonnées de façon déterministe et les doublons sont rejetés.
4. Le modèle de bulletin et sa version sont explicites; la marque est un instantané, pas une lecture dynamique qui altérerait les anciens documents.
5. Le logo est référencé par un identifiant d'actif, jamais par une URL arbitraire fournie par le client.
6. L'empreinte permet de détecter une modification du contenu; elle ne remplace ni une signature institutionnelle ni un stockage immuable.
7. L'API future devra recharger les résultats avec RLS dans le tenant/organisation actifs et vérifier les permissions parent/élève/enseignant/administration.
8. La publication devra être transactionnelle, idempotente, auditée et émise via l'Outbox; une republication crée une nouvelle révision, elle ne réécrit jamais le bulletin publié.
9. Aucun frais, montant, paiement, bourse ou solde n'est calculé ici. Financial Core reste l'unique autorité financière.

## Code ajouté

- `tests/p056-8-bulletin-snapshot.test.ts`: complétude, immutabilité, déterminisme, version du modèle, année académique, marque, doublons et états incomplets.

## Hors périmètre explicite
Cette première tranche n'ajoute pas encore de table, route HTTP, PDF, signature, stockage de fichier ni portail parent. Le registre Bible indique que DB-074 n'est pas présent dans le dépôt : aucune interface Web/Mobile concurrente ne doit être inventée ici. Le prochain lot raccordera le snapshot à une API transactionnelle et au service documentaire existant après inventaire du stockage et des moteurs PDF.

## Migration, publication et rollback
Aucune migration dans cette tranche. À l'étape de persistance, prévoir une migration additive avec contraintes uniques par organisation/élève/période/révision, version optimiste, RLS FORCE, rôle runtime minimal et stratégie de conservation des révisions. Désactiver les routes de publication en cas d'incident; ne jamais effacer un document déjà remis.

## Validation
Les tests unitaires sont ajoutés, mais aucun test n'est déclaré exécuté. Le CI du SHA final doit couvrir typecheck, tests Node, Security Fortress, PostgreSQL 17, Web build, audit dépendances et Android. La PR reste non fusionnée jusqu'à ces preuves.
