# TONTINE-CASE-PERSISTENCE-002 — Durable case operations\n\n## Scope\nImplement the existing tontine_cases, tontine_case_evidence, tontine_targeted_holds and tontine_refund_requests domain as tenant-scoped PostgreSQL operations. This is an operational case-management layer for the independent Community Tontine domain.\n\n## Bible and ADR constraints\n- docs/skills/TPAY-TONTINE-CYCLE-001.md: dispute, exception, recovery and refund workflows; never silently correct a financial mismatch.\n- docs/skills/TPAY-FIN-002.md: Financial Core remains the sole posted-money authority.\n- docs/skills/TPAY-SEC-001.md and docs/security/THREAT-MODEL.md: tenant binding, fail-closed access, append-only evidence and auditability.\n- docs/architecture/ADR-004-community-tontine.md: Community Tontine remains independent from partner microfinance.\n- docs/architecture/ADR-021-payout-reconciliation-reversal.md: reversals are compensating Financial Core transactions, never edits to ledger history.\n\n## Implemented\n1. PostgresTontineCaseRepository provides create/read and compare-and-set state transitions.\n2. Every case lookup and mutation is organization-scoped.\n3. Case transitions are validated against the existing domain state machine.\n4. Evidence insertion requires a same-tenant parent case and a SHA-256 content hash; raw evidence bytes are not stored in the case table.\n5. Targeted holds are created only against a same-tenant case and can be released only once.\n6. Refund requests require exactly one original contribution or payout reference and a positive integer-minor-unit amount.\n7. Refund state transitions are explicit. A refund cannot jump from approved directly to settled; it must pass through submitted_to_financial_core.\n8. Migration 116 adds composite organization/group and organization/case foreign keys, work-queue indexes and append-only evidence enforcement.\n\n## Deliberate boundary\nThis repository does not execute refunds, alter balances, or write ledger entries. submitted_to_financial_core is a workflow handoff state, not proof of settlement. A future adapter must invoke the canonical Financial Core compensating-transaction API and reconcile its authoritative result.\n\n## Validation\n- Added focused repository tests for tenant-scoped compare-and-set, invalid transitions, missing/cross-tenant parent case, evidence hash validation, refund transition guards and one-time hold release.\n- GitHub Actions must execute TypeScript, unit and live PostgreSQL suites against the final PR head. No local or CI test success is claimed by this construction record.\n\n## Rollback\nMigration 116 adds constraints/indexes and an evidence immutability trigger. Rollback is not an automatic destructive drop: first verify no production case/evidence/hold/refund records depend on these constraints. Preserve all financial evidence and ledger history.
