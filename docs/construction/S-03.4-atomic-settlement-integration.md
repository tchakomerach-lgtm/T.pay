# S-03.4 — Atomic Ledger + Fee + Contribution Settlement Integration

## Decision

The provider-confirmed contribution is settled as one database transaction. The transaction owns:
provider-event claim → ledger idempotency check → balanced Ledger append → immutable fee snapshot → contribution confirmation → payment settlement → receipt → outbox.

Provider network calls and callback authentication remain outside this financial transaction.

## Accounting invariant

The settlement input must describe one gross amount consistently across contribution, payment intent, verified provider event, receipt and Ledger debit/credit totals.

The fee snapshot must satisfy: microfinance fee >= 0; T.Pay fee >= 0; total fee = microfinance fee + T.Pay fee; total fee <= gross contribution; same contribution and currency.

The Ledger remains balanced and uses integer minor units. The fee snapshot is evidence of the versioned calculation; it is not a second source of money.

A typical contribution accounting shape is:
- debit provider/cash clearing: gross;
- credit tontine/member liability: gross - fees;
- credit microfinance fee payable: microfinance fee;
- credit T.Pay fee income: T.Pay fee.

The actual account mapping is supplied by the organization/ledger factory and is never inferred from provider data.

## Security / threat gate

- Duplicate callback: organization-scoped ledger idempotency + (provider,event_id) database uniqueness.
- Cross-organization settlement: organization is checked before and after row locks.
- Amount manipulation: exact bigint comparisons across all financial representations.
- Fee manipulation: immutable fee snapshot consistency gate.
- Partial settlement: every financial/evidence write is inside the same transaction.
- Provider event false-positive: invalid evidence is rejected before durable claim.
- Crash after ledger write: transaction rollback prevents partial contribution/payment/receipt/outbox state.
- Serialization/deadlock: PostgreSQL transaction adapter retries the complete transaction with bounded attempts.
- Offline/provider retry: same idempotency identity remains authoritative.

PostgreSQL documents that serializable transactions can fail with SQLSTATE 40001 and must be retried as a complete transaction; unique constraints provide the database uniqueness barrier. OWASP recommends idempotency and transactional locking for concurrent business operations.

## Tests
