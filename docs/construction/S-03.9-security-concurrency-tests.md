# S-03.9 — Security / Concurrency / Duplicate-Provider Hardening

## Scope
Adversarial proof layer for the Settlement Orchestrator. This brick does not add a second financial mechanism; it proves the existing Ledger, provider-event replay barrier and settlement state machine resist concurrent/replayed inputs.

## External research
- PostgreSQL 18 transaction isolation: Serializable transactions must be prepared for serialization failures; SQLSTATE 40001 is the serialization-failure signal. The existing repository already retries 40001 and 40P01. Adopted. https://www.postgresql.org/docs/current/transaction-iso.html
- PostgreSQL 18 serialization failure handling: retry 40001 and, where appropriate, 40P01; unique-key failures are distinct and must not be blindly treated as transient. Adopted as a test/design constraint. https://www.postgresql.org/docs/current/mvcc-serialization-failure-handling.html
- OWASP Business Logic Security: concurrency is a business-logic threat; sensitive check-and-act operations require atomic transactions/locks/conditional writes and idempotency. Adopted. https://cheatsheetseries.owasp.org/cheatsheets/Business_Logic_Security_Cheat_Sheet.html
- OWASP Third Party Payment Gateway Integration: validate server-side amount/currency/order identity, authenticate callbacks, reject replay and process callbacks idempotently. Adopted. https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Payment_Gateway_Integration_Cheat_Sheet.html

## Threat gate
- Assets: Ledger postings, contribution/payment terminal states, provider-event claims, receipt/outbox side effects.
- Trust boundaries: external provider callback -> T.Pay security boundary -> settlement transaction -> PostgreSQL.
- Replay: covered by callback claim and provider event uniqueness.
- Double execution: covered by organization-scoped Ledger idempotency and serialized settlement.
- Cross-organization collision: provider event ownership is checked and rejected when an existing event belongs to another organization.
- Contradictory provider data: provider/payment identity, amount, currency and accepted-state checks reject before persistence.
- Concurrency: serializable transaction plus row locks and DB uniqueness remain authoritative.
- Safe failure: reject/quarantine; never auto-correct Ledger state from a mismatch.
- Evidence: durable provider event, Ledger idempotency, reconciliation exception boundary and existing audit/event paths.

## Acceptance criteria
1. A contradictory provider event cannot reach financial persistence.
2. Replaying the same signed callback cannot claim the event twice.
3. Concurrent settlement with one contribution idempotency key produces one Ledger effect.
4. A provider event cannot be reassigned across organizations.
5. The same Ledger idempotency key is isolated by organization but unique inside one organization.
6. Existing retry policy for 40001/40P01 remains intact.
7. No sensitive data is added to logs or test output.

## Remaining risk
The live tests exercise the database constraints and settlement primitives, but real provider credentials/network calls remain intentionally disconnected. Future live-provider integration must preserve these invariants and add provider-specific contract tests.
