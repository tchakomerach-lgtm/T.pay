# P057.1 — Tenant-bound device and session credentials

## Bible and architecture alignment
Mandatory sources consulted: `AGENTS.md`, `docs/bibles/TPAY-BIBLE-CONSULTATION-REGISTRY.md`, `docs/bibles/IMPLEMENTATION-MAP.md`, `docs/skills/TPAY-CONSTRUCTION-001.md`, `docs/skills/TPAY-AUTH-002.md`, `docs/skills/TPAY-SEC-001.md`, `packages/identity`, `packages/security`, L13.1 device/session persistence, and P056.3 temporal authorization.
This brick extends the existing identity/device/session boundary; it does not introduce a second identity provider or authorization evaluator.

## Credential contract
- Access bearer format: `tpay1.<tenantId>.<high-entropy-secret>`.
- The tenant segment is an untrusted routing claim, never an authorization grant. The server hashes the complete bearer and requires a matching persisted session row with the same tenant.
- Only SHA-256 hashes are persisted; raw bearer values are returned once to the local bootstrap operator and are never logged.
- Device and session records carry tenant_id. Device verification, revocation, session creation and validation always include tenant_id in predicates.
- Session creation binds tenant, actor, device and trust_epoch. Expired, revoked, locked, mismatched or stale-epoch sessions fail closed.
- Existing sessions without a resolvable tenant are revoked by migration 124; users must authenticate again.

## API runtime integration
The production API extracts the tenant routing claim from the bearer, validates the complete bearer against the tenant-bound session row, then verifies the actor against the same tenant and organization. The tenant value is still untrusted until both database checks pass.

## Migration and compatibility
Migration 124 adds tenant_id to existing device/session tables, backfills it only from education_actors, revokes unresolved legacy sessions, and adds tenant-scoped indexes. NULL tenant_id is legacy-only; repository writes reject it.

- Persist identity principal lifecycle and membership changes; ensure organization switching creates a distinct session security context.

- Implement session refresh rotation and per-session revocation APIs with atomic audit/outbox.
- Add live PostgreSQL 17 tests under a non-owner, non-superuser, NOBYPASSRLS login; prove tenant A cannot read/revoke tenant B.
