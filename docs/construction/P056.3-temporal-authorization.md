# P056.3 — Autorisations temporelles et isolation des droits

## Portée livrée dans cette extension

- La migration 120 transforme `api_actor_permissions` en historique de grants : identifiant de grant, début de validité, expiration facultative, révocation horodatée, auteur et motif.
- Les grants historiques sont conservés ; une révocation met fin à l'autorisation sans supprimer la trace.
- Le serveur API ne charge que les permissions actives à l'instant de l'authentification : `valid_from <= now`, `valid_until IS NULL OR valid_until > now`, `revoked_at IS NULL`.
- La lecture des permissions passe par `tpay_school_runtime`, avec contexte transactionnel `tpay.tenant_id` et `tpay.organization_id`.
- RLS est activé et forcé sur `api_actor_permissions`; la policy runtime ferme l'accès hors du tenant et de l'organisation présents dans les GUC transactionnels.
- Le test d'intégration P056.3 couvre un grant actif, futur, expiré et révoqué sur PostgreSQL réel.

## Invariants

1. Une permission n'est effective que pendant son intervalle de validité et avant révocation.
2. Une permission d'une autre organisation ou d'un autre tenant ne doit pas être visible au runtime.
3. Le rôle runtime ne reçoit pas de droit DELETE sur l'historique des grants.
4. L'expiration de session reste contrôlée indépendamment de l'expiration du grant.
5. L'API échoue fermée si le rôle runtime, le contexte tenant/organisation ou la lecture des grants échoue.

## Travaux encore requis avant clôture de P056.3

- Routes authentifiées de création, consultation, expiration anticipée et révocation des grants, protégées par `security.manage`, avec motif obligatoire et audit transactionnel.
- Tests PostgreSQL avec un login applicatif non-propriétaire, sans superuser ni `BYPASSRLS`, et essais négatifs croisés tenant/organisation.
- API authentifiées pour affectations, évaluations, notes et bulletins, avec contrôle d'accès par rôle, classe, période et état de validation.
- Adaptateur Financial Core pour les frais scolaires : création d'intents uniquement, comptes vérifiés dans la même organisation, XOF, idempotence, approbation humaine et aucune écriture scolaire dans le Ledger.
- Tests de rollback, concurrence, rejeu, Outbox et audit sur ces nouvelles routes.

## Gates de validation

- `npm run check`
- `npm run security:fortress`
- `npm run test:postgres` sur PostgreSQL 17 réel avec `TPAY_DATABASE_URL`
- Build Web et vérification visuelle des flux
- Build APK Android et essai sur appareil
- Résultats CI verts sur le SHA exact, plus preuve que le rôle runtime n'est ni propriétaire, ni superuser, ni `BYPASSRLS`

Aucune fusion, certification ou ouverture de P058 n'est autorisée par la seule présence de cette migration ou de ce test.
