# P056.2 — Opérations scolaires transactionnelles

## Portée

Cette séquence étend le contrat P056.1 aux opérations Présences, Tâches et Demandes de services. Les mutations utilisent le `PostgresSchoolMutationUnitOfWork` et un seul client PostgreSQL réservé.

## Invariants

1. Le rôle `tpay_school_runtime` est activé localement dans la transaction.
2. `tpay.tenant_id` et `tpay.organization_id` sont définis avec `set_config(..., true)` à partir du contexte authentifié.
3. La mutation métier, l'audit, l'événement `education_transactional_outbox` et la complétion idempotente sont validés dans le même commit.
4. Un échec avant COMMIT annule la mutation, l'audit, l'événement et la complétion idempotente.
5. Aucune publication réseau directe n'est exécutée pour les routes couvertes. Le dispatcher Outbox reste l'unique voie de diffusion.
6. Les transitions des tâches et services utilisent une version optimiste et refusent les mises à jour concurrentes obsolètes.
7. Les présences sont réconciliées avec les règles métier de correction explicite avant écriture.

## Routes couvertes

| Route | Mutation | Événement |
|---|---|---|
| `POST /v1/education/attendance` | Upsert versionné après réconciliation | `attendance.changed` |
| `POST /v1/education/work-items` | Création | `work_item.changed` |
| `POST /v1/education/work-items/:id/claim` | Attribution versionnée | `work_item.changed` |
| `POST /v1/education/work-items/:id/resolve` | Résolution versionnée | `work_item.changed` |
| `POST /v1/education/service-requests` | Création | `service_request.changed` |
| `POST /v1/education/service-requests/:id/transition` | Transition métier versionnée | `service_request.changed` |

## Migration PostgreSQL

`119_p056_2_school_operations_runtime_rls.sql` active et force RLS pour `education_attendance`, `education_work_items` et `education_service_requests`, crée les politiques à fermeture par défaut et accorde au rôle runtime uniquement les opérations nécessaires.

Le déploiement doit provisionner explicitement l'appartenance du login API au rôle runtime. Le processus applicatif ne doit pas utiliser un propriétaire de table, un superutilisateur ou un rôle `BYPASSRLS`.

## Validation attendue

- `npm run test:postgres` sur PostgreSQL 17 réel.
- `npm run check`.
- `npm run security:fortress`.
- `npm run web:build` et audit des dépendances.
- Tests d'isolation entre tenants/organisations sur les trois tables.
- Tests de rollback audit/outbox, idempotence, conflits de version et claims Outbox concurrents.
- Vérification de l'interface et du build Android sur le SHA final.

## Limites connues

- Le flux de synchronisation offline conserve encore son adaptateur Outbox dédié : son raccordement à l'Outbox transactionnelle centrale doit être une séquence séparée avec tests de rejeu et de conflit.
- Les API de gestion des notes, évaluations, bulletins, affectations et frais scolaires restent à couvrir par leurs propres transactions et contrats d'autorisation.
- Une publication Outbox est au moins une fois. Les consommateurs doivent dédupliquer par `event_id`.
- Cette séquence n'est pas certifiée tant que toutes les validations ci-dessus ne sont pas vertes sur le commit exact.

## Revue de sécurité complémentaire — lecture des acteurs

La route `GET /v1/education/actors/:actorId` doit utiliser le même contexte PostgreSQL contraint que les autres lectures organisationnelles. Toute lecture métier passe par `executeSchoolRead`, qui ouvre une transaction, applique `SET LOCAL ROLE tpay_school_runtime`, définit le tenant et l'organisation avec `set_config(..., true)`, puis exécute la requête avant COMMIT. Les prédicats explicites tenant/organisation restent conservés en défense en profondeur.

Correction portée par les commits `a4133f16` et `3a2956c9`. Le test HTTP vérifie le rôle runtime, le contexte tenant et l'exécution de la lecture dans le client transactionnel. La validation PostgreSQL réelle sous login runtime non propriétaire, non-superuser et `NOBYPASSRLS` reste obligatoire.
